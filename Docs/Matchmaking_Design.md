# 매치메이킹 시스템 기획서

리그오브레전드의 매치메이킹~챔피언 선택 과정을 클론한다. **매칭 시작부터 픽 완료(게임 시작 트리거)까지**가 범위이며, 실제 인게임 전투/스킬/승패 판정은 이 기획의 범위 밖이다.

---

## 1. 개요

### 1.1 목표
플레이어가 "매칭 시작"을 누르면:
1. MMR이 비슷한 10명(팀 5명 × 2팀)이 모이고
2. 각자 포지션(탑/정글/미드/원딜/서폿)이 배정되고
3. 챔피언 선택 화면에서 포지션별로 챔피언을 고르고
4. 모두 픽을 마치면 "게임 시작" 상태로 전환된다.

### 1.2 범위 밖
- 실제 전투/스킬/아이템/승패 판정 등 인게임 로직
- 밴(ban) 단계 — 픽만 구현 (밴은 확장 과제로 남김)
- 매치메이킹 정확도를 위한 정교한 레이팅 알고리즘(Elo/Glicko 등 실제 공식) — 여기서는 단순화된 MMR 차이 기반 매칭만 다룸
- **DB/영속성 저장** — MMR, 대기열, 매치, 픽 상태 등 이 기능과 관련된 모든 데이터는 **인메모리로만** 관리한다. `GameDB.xml`/`DBSynchronizer`(현재 동기 호출이라 잡 큐와 분리 안 된 상태 — 알려진 기술 부채) 쪽은 이번 기능에서 건드리지 않는다. 서버가 재시작되면 MMR을 포함한 모든 매치메이킹 상태는 초기화된다.

---

## 2. 핵심 개념

### 2.1 MMR (Match Making Rating)
- 플레이어의 실력을 나타내는 정수값. 매칭의 핵심 기준. **인메모리에서만 관리**(DB 저장 없음, 서버 재시작 시 초기화).
- **클라이언트에게 절대 노출하지 않는다** — 어떤 `.proto` 메시지에도 `mmr` 필드를 두지 않는다. 매칭 계산은 서버 프로세스 내부에서만 이뤄지고, 클라이언트가 자기 MMR을 서버에 보내는 경로 자체가 없다(치팅 방지 — MMR은 항상 서버가 들고 있는 값만 신뢰).
- DB가 없으므로, 로그인 시 **닉네임 기준으로 서버가 랜덤 MMR을 생성**한다. 같은 닉네임으로 재접속하면 **서버 프로세스가 살아있는 동안은 MMR이 유지**되도록, 닉네임 → MMR 매핑을 별도의 인메모리 저장소(예: `HashMap<string, uint32>`를 가진 매니저)에 캐싱한다 — DB 영속화는 아니지만, 같은 서버가 떠 있는 동안은 재접속해도 MMR이 흔들리지 않아야 매칭 테스트가 의미 있음. 서버가 재시작되면 이 캐시도 초기화된다.
- 매칭 시 **MMR 차이가 ±200 이내인 플레이어들**을 모아 팀을 구성한다(고정값, 대기 시간에 따라 넓어지지 않음 — 4.2 참고).

### 2.2 포지션 (Position)
```
TOP, JUNGLE, MID, ADC, SUPPORT
```
- 한 팀은 반드시 5개 포지션이 정확히 하나씩 채워져야 한다.
- 플레이어는 매칭 신청 시 **선호 포지션**을 지정하며, 아래 세 가지를 전부 지원한다:
  - 1지망 (`primary`)
  - 2지망 (`secondary`)
  - 상관없음/자동 (`fill`) — 어느 포지션이든 배정 가능
- 매칭 알고리즘은 "MMR 조건을 만족하면서 5개 포지션이 다 채워지는 조합"을 찾아야 한다 — 단순 MMR 매칭보다 한 단계 복잡한 제약 조건.

### 2.3 매치메이킹 티켓 (Matchmaking Ticket)
- 플레이어가 "매칭 시작"을 누르는 순간 발급되는, "이 사람은 지금 매칭 대기 중"이라는 상태를 나타내는 단위. **인메모리에서만 관리.**
- 대기열은 **30초 주기**(조절 가능한 설정값)로 검사되어 매칭을 시도한다.

## 3. 전체 흐름

```
① 클라이언트: "매칭 시작" 버튼 -> C_MATCH_START(1지망/2지망/상관없음) 전송
② 서버: MatchmakingQueue에 티켓 등록, S_MATCH_QUEUED(대기 시작) 응답
③ 서버: 30초 주기로 대기열을 검사해서 매칭 가능한 10명 조합 탐색
④ 매칭 성사: 10명에게 S_MATCH_FOUND(팀 정보, 배정된 포지션, 상대팀 정보) 전송
⑤ 자동 수락 — 별도 수락 단계 없이 매칭 성사 즉시 챔피언 선택으로 진입한다
⑥ 챔피언 선택 세션(ChampSelect) 생성, S_CHAMPSELECT_START로 10명 모두 입장
⑦ 각자 C_PICK_CHAMPION(챔피언ID) 전송 -> 서버가 검증(중복 픽 불가) 후 S_PICK_UPDATE로 전원에게 브로드캐스트
⑧ 10명 전원 픽 완료 -> S_GAME_START(최종 팀 구성 + 각자 챔피언) 전송, 매치메이킹 종료
```

## 4. 매치메이킹 알고리즘

### 4.1 큐 등록
- 플레이어가 매칭을 신청하면 `MatchmakingTicket { playerId, mmr, primaryPosition, secondaryPosition, queuedAt }`을 생성해 대기열에 넣는다. 포지션에 "상관없음"을 선택했다면 `primary`/`secondary` 둘 다 "FILL"로 표시.
- 매칭 시도 주기는 **기본 30초**이되, 코드상 상수/설정값으로 빼서 조절 가능하게 만든다(`MatchmakingConfig::TickIntervalSec` 같은 형태).

### 4.2 후보 탐색 (30초 주기로 실행)
1. 대기 시간이 긴 티켓부터 우선적으로 매칭을 시도한다(오래 기다린 사람을 먼저 구제).
2. 기준 티켓의 MMR을 중심으로 **±200 이내**인 티켓들을 후보로 추린다(고정 범위 — 시간에 따라 넓어지지 않음).
3. 후보 중에서 5개 포지션이 정확히 하나씩 채워지는 5명 조합을 2세트(양 팀) 찾는다.
   - 포지션 배정 우선순위: **1지망 → 2지망 → 상관없음(FILL)** 순으로 시도해서 빈 포지션을 채운다.
4. **팀 밸런싱**: 확보된 10명(양 팀 조합 후보)을 MMR 내림차순으로 정렬한 뒤, 지그재그(1,4,5,8,9번째는 A팀 / 2,3,6,7,10번째는 B팀 식)로 분배해서 두 팀의 **평균 MMR이 최대한 비슷하도록** 5명씩 맞춘다.
5. 후보 풀에 10명이 안 모이거나 포지션 조합이 안 맞으면 이번 주기는 매치 미성사 — 다음 30초 주기에 다시 시도(티켓은 계속 대기열에 남아있음, MMR 범위는 그대로 ±200 유지).

### 4.3 이 프로젝트 구조에 매핑
- **대기열 처리**: 매칭 로직 자체가 "여러 스레드가 동시에 건드릴 수 있는 공유 상태"이므로, `JobQueue`를 상속받는 `MatchmakingManager` 하나가 전담하는 구조를 추천 — `Room`이 `JobQueue`를 상속받아 락 없이 안전하게 처리했던 패턴을 그대로 재사용.
- **주기적 매칭 시도**: `JobTimer::Reserve`(지금까지 본 지연 실행 예약)로 "N초 뒤에 다시 매칭 시도"를 반복 예약하는 방식으로 구현 가능.
- **매치 성사 후**: 확정된 10명을 위한 `ChampSelectSession`(임시 `Room`과 유사한 개념, 역시 `JobQueue` 상속 후보)을 하나 생성해서 그 안에서만 픽 관련 패킷을 주고받게 한다.

## 5. 챔피언 선택 (ChampSelect)

### 5.1 세션 생성
- 매치 성사 시 `ChampSelectSession`을 하나 만들고, 10명의 `PlayerRef`(또는 세션 참조)를 각자의 배정된 포지션과 함께 등록한다.
- 각 플레이어의 `GameSession`에 "지금 어느 ChampSelectSession에 속해 있는지"를 저장한다 — `GameSession::_room`이 `weak_ptr<Room>`이었던 것처럼, 여기서도 소유권 방향에 주의(`ChampSelectSession`이 참가자들을 강하게 들고 있고, 참가자는 세션을 약하게 참조하는 쪽을 추천).

### 5.2 픽 진행
- 단순화된 규칙(밴 없음, 순서 제약 없음)으로 시작: 10명이 각자 원하는 타이밍에 자유롭게 챔피언을 고른다.
- 서버는 `C_PICK_CHAMPION(champId)`을 받으면:
  1. 이미 같은 팀/상대팀에서 그 챔피언이 픽됐는지 검증(중복 불가 — 리그오브레전드는 팀 간에도 중복 불가).
  2. 유효하면 해당 플레이어의 픽 상태를 갱신하고, 세션 참가자 전원에게 `S_PICK_UPDATE(playerId, champId)`를 브로드캐스트.
  3. 유효하지 않으면 요청한 본인에게만 실패 응답.

### 5.3 완료 판정
- 10명 전원이 픽을 완료하면 `S_GAME_START`를 전원에게 전송하고 `ChampSelectSession`을 정리(리소스 해제).

### 5.4 이탈(dodge) 처리 — 확장 과제로 남김
- 픽 도중 한 명이 접속을 끊으면 어떻게 할지(전체 매칭 취소 / 봇으로 대체 / 페널티 부여)는 이번 범위에서는 "매칭 취소 후 나머지 9명 재대기열 등록" 정도의 단순 처리로만 명시하고, 실제 페널티 시스템은 추후 확장.

## 6. 데이터 모델 초안

```
MatchmakingTicket
	playerId, mmr, primaryPosition, secondaryPosition, queuedAt   // FILL 포함

Team
	teamId, players[5] (playerId + position 매핑), averageMmr

Match
	matchId, team1: Team, team2: Team, createdAt

ChampSelectSession (JobQueue 상속 후보)
	matchId, participants[10] { playerId, position, pickedChampionId }
```

## 7. 패킷(프로토콜) 초안

`Protocol.proto`에 추가할 메시지 후보:

```protobuf
message C_MATCH_START
{
	Position primaryPosition = 1;    // FILL(상관없음) 값을 enum에 포함
	Position secondaryPosition = 2;  // FILL이면 2지망 없음
}
message S_MATCH_QUEUED { }

message S_MATCH_FOUND
{
	uint64 matchId = 1;
	repeated PlayerInfo myTeam = 2;
	repeated PlayerInfo enemyTeam = 3;
	Position myPosition = 4;
}

message C_PICK_CHAMPION { uint32 championId = 1; }
message S_PICK_UPDATE { uint64 playerId = 1; uint32 championId = 2; }
message S_CHAMPSELECT_START { uint64 matchId = 1; repeated PlayerInfo participants = 2; }
message S_GAME_START { uint64 matchId = 1; repeated PlayerInfo finalTeams = 2; }
```
(`Position` enum, `PlayerInfo` 메시지는 `Enum.proto`/`Struct.proto`에 추가 필요 — 지금 있는 `PlayerType`은 챔피언 타입이 아니라 이 프로젝트 초기 스캐폴딩의 "직업"이라 별도로 `Position` enum을 새로 정의하는 게 맞다.)

## 8. 결정된 사항 요약

| 항목 | 결정 |
|---|---|
| 매칭 시도 주기 | 30초 (설정값으로 조절 가능하게 구현) |
| MMR 허용 범위 | ±200 고정 (시간에 따라 확장 안 함) |
| 팀 밸런싱 | 5명씩 나눠서 두 팀 평균 MMR 비슷하게 (지그재그 분배) |
| 포지션 선호 | 1지망 / 2지망 / 상관없음(FILL) 전부 지원 |
| 매칭 수락 단계 | 없음 — 매치 성사 즉시 자동으로 챔피언 선택 진입 |
| DB/영속성 | 사용 안 함 — 전부 인메모리, 서버 재시작 시 초기화 |

### 남은 열린 질문
- 대기 시간이 길어져도 클라이언트에게 "예상 대기시간" 등의 피드백은 **주지 않는다** — 대기 중 상태만 유지(결정 완료).
- 지그재그 분배로 평균 MMR을 맞출 때, 포지션별 인원이 고정(팀당 각 포지션 1명)이라 "MMR 정렬 후 지그재그"가 포지션 제약과 충돌할 수 있음(예: 탑 지원자가 2명뿐이면 그 둘의 MMR 순서가 그대로 지그재그를 결정) — 실제 구현하면서 후보 수가 적은 초반 테스트 환경(더미 클라이언트로 10명 미만 접속) 기준으로 로직을 먼저 검증하는 게 좋겠음.

### 보류 중 — MMR 계산(게임 결과 반영) 방식
게임 종료 후 승/패에 따라 MMR을 얼마나 올리고 내릴지(고정값 / 상대 팀과의 MMR 차이 반영 / 팀 내 개인 기여도 반영 등)는 아직 설계가 정해지지 않았다. 이 기획서의 범위(매칭~픽) 자체는 "현재 MMR 값을 읽어서 매칭에 쓰는" 것까지만 다루므로 구현을 막지는 않지만, MMR 증감 로직은 별도로 더 생각해본 뒤 확정한다.
